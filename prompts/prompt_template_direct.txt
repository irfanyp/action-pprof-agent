## Reference Level

The "reference level" controls how thorough your analysis and fix should be, and which remediation effort tier you are allowed to implement:
- **low**:  Focus on the single highest-impact hotspot. Implement only a **low-effort** fix (Option A below), touching only the file(s) needed for that one hotspot.
- **med**:  Address the top hotspots. Implement **low- or medium-effort** fixes (Option A or B); no large refactors or unrelated files.
- **high**: Perform a comprehensive analysis. Address all significant hotspots that are actually backed by the profile data, and you may implement **medium- or high-effort** fixes (Option A, B, or C) where justified — but this is not license for open-ended refactors unrelated to the hotspots found.

For each application-code hotspot you decide to fix, briefly weigh three remediation tiers before choosing which one to implement:
- **Option A (low effort):** safe, localized tweaks — pre-allocating, avoiding redundant work, hoisting invariants out of loops.
- **Option B (medium effort):** algorithmic improvements or logic changes confined to the function/package.
- **Option C (high effort):** architectural changes or replacing a dependency.
Only implement the tier(s) permitted by the current reference level. If a higher-effort tier would fix the issue better but is out of scope for this reference level, mention it briefly in SUMMARY as a follow-up option rather than implementing it.

Sample counts matter: a hotspot backed by very few samples (e.g. a handful out of a short profile) is statistically noisy, not necessarily significant. If the profile has low total sample counts, say so explicitly in SUMMARY and treat any resulting "fix" as low-confidence rather than asserting certainty. If the total sample count is very low (e.g. fewer than ~20 samples), default to the "no application-level fix" path unless a single hotspot accounts for a clear majority of samples AND maps to application code. State the sample count and this reasoning in SUMMARY.

## Your Task

0. ⚠️ **At the moment**, the `**Type:**` field (e.g. "Application code") in the analyzer result is produced by a heuristic and is **known to be unreliable** — it frequently mislabels `runtime.*`/`syscall.*`/`text/tabwriter.*` and other non-repository frames as "Application code." **Disregard it.** This is a temporary measure until a more accurate classifier is integrated. Perform your own classification per the rules below.

1. For each hotspot, walk its call stack and classify it as either:
   - **Application code**: a frame in the hotspot's own stack trace is defined in a file present in the repository.
   - **Non-application code**: every frame is Go runtime/stdlib (e.g. `runtime.*`, `syscall.*`, `net/http.*`, `text/tabwriter.*`) or a third-party dependency whose source is not present in the repository.
   Only treat the "Application code" hotspots as candidates for a source fix — you cannot patch code that isn't in the repository.

   No pre-built file list is provided here — use your native search/list-file tools to find the Go source files in the repository whose basenames match the hotspots' stack frames. When matching, compare by the **file basename** (or trailing path segments), since profile paths are absolute while repository paths are repo-relative. Note that generated files like `_testmain.go` are never present in the repository and are never actionable.
2. Correlate each application-code hotspot with the repository source and identify its root cause. Use your native file-reading tool to inspect the relevant source files. Ignore repository files that are unrelated to the flagged call stacks (docs, unrelated tests, fixtures) unless a hotspot's own stack trace points into them.
3. Apply fixes directly to the repository source files using your native file-editing tools, respecting the scope described for the current reference level above.

## If No Application-Level Fix Is Possible

If every significant hotspot is non-application code (runtime/stdlib/third-party, not present in the repository), or the profile has too few samples to justify a code change, do not invent a fix. Instead:
- State this clearly in SUMMARY, naming the hotspots and why they aren't actionable (e.g. "all hotspots are in the Go runtime/stdlib and not present in this repository").
- If there is a relevant call site in the repository, you may add a brief inline code comment near it noting the observed cost and why it isn't fixable at the application level. Otherwise, make no code change and explain why in SUMMARY.

**For comment-only changes, use inline comments** (appending to existing lines, not adding new lines) to minimize whitespace risks. Example: `return false // Early return for nil checks` instead of adding a new comment line above it.

## Output Format

Respond with a single section:

### SUMMARY

Structure this section as:

1. An "Executive Summary" markdown table, one row per hotspot you analyzed:

   | ID | File Path | Function | Self % (measured) | Max Theoretical Reduction* | Confidence | Priority (1-5) |
   |---|---|---|---|---|---|---|

   - `Self % (measured)`: the hotspot's self% (or cum%, if you're fixing the whole subtree beneath a call) exactly as reported in the analyzer result — a measured fact, not an estimate.
   - `Max Theoretical Reduction*`: an Amdahl's-law **upper bound**, equal to that same self%/cum% figure — the largest possible drop in total CPU time if this hotspot's cost were fully eliminated, assuming everything else unchanged. State which basis (self or cum) you used. Never present this as a predicted or guaranteed outcome, and never invent a number not directly derivable from the analyzer result.
   - `Confidence`: driven by the profile's total sample count (e.g. "Low (n=4)", "High (n=5000)") — low sample counts mean wide statistical uncertainty on the self%/cum% figures themselves, so say so here rather than in prose only.
   - For hotspots classified as non-application code (not fixed), still list them with a `Priority` of "N/A" and a short reason in `Function` (e.g. "runtime.memclrNoHeapPointers — not in this repository").

   Footnote below the table: `* Amdahl's-law upper bound assuming the fix fully eliminates this hotspot's measured cost. It is not a prediction of the fix's actual effect — re-profile after applying the patch to measure the real result.`

2. A concise prose explanation, per hotspot fixed, of the root cause and the fix you applied to the source files (or, per the section above, why no application-level fix was possible). Since you are editing files directly, describe which files you changed and what you changed in each.

Do not include any introductory or concluding conversational text outside the ### SUMMARY header — no preamble like "Here is my analysis", no closing remarks.
