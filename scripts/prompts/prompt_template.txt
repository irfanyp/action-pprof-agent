## Reference Level: {reference_level}

The "reference level" controls how thorough your analysis and fix should be:
- **low**:  Focus on the single highest-impact hotspot. Produce a minimal, targeted patch that touches only the file(s) needed to fix that one hotspot.
- **med**:  Address the top hotspots. Produce a focused patch that fixes the main issues without large refactors or touching unrelated files.
- **high**: Perform a comprehensive analysis. Address all significant hotspots that are actually backed by the profile data, and produce a thorough patch — but do not use this as license for open-ended refactors unrelated to the hotspots found.

Sample counts matter: a hotspot backed by very few samples (e.g. a handful out of a short profile) is statistically noisy, not necessarily significant. If the profile has low total sample counts, say so explicitly in SUMMARY and treat any resulting "fix" as low-confidence rather than asserting certainty.

## If No Application-Level Fix Is Possible

If every significant hotspot is non-application code (runtime/stdlib/third-party, not present in the repository), or the profile has too few samples to justify a code change, do not invent a fix. Instead:
- State this clearly in SUMMARY, naming the hotspots and why they aren't actionable (e.g. "all hotspots are in the Go runtime/stdlib and not present in this repository").
- Still produce a PATCH, but make it a minimal, behavior-preserving change such as a code comment near the relevant call site (e.g. noting the observed cost and why it isn't fixable at the application level). Never leave the PATCH section empty.

## Output Format

Respond with exactly two sections:

### SUMMARY

A concise explanation of the problems found and the fixes applied (or, per the section above, why no application-level fix was possible). This will be used as the Pull Request description. Do not include any ``` code fences in this section — save all fenced code for the single fence in PATCH.

### PATCH

A single unified-diff patch wrapped in one ```diff code fence — the only code fence in your entire response. If multiple files change, include all of their hunks inside this one fence; do not split the patch across multiple fences.

The patch must be applicable with `git apply` from the repository root:
- File paths in the `--- a/...` / `+++ b/...` headers must exactly match the paths shown in the repository XML above.
- Each hunk's `@@ -a,b +c,d @@` header line counts must accurately reflect the number of context/removed/added lines that follow.
- For new files, use `--- /dev/null` as the source path.
- Only include files that need to change.

Example:

```diff
--- a/path/to/file.go
+++ b/path/to/file.go
@@ -10,7 +10,7 @@
 context line
-old line
+new line

```
