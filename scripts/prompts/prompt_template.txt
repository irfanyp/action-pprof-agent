## Reference Level: {reference_level}

The "reference level" controls how thorough your analysis and fix should be, and which remediation effort tier you are allowed to implement in the patch:
- **low**:  Focus on the single highest-impact hotspot. Implement only a **low-effort** fix (Option A below), touching only the file(s) needed for that one hotspot.
- **med**:  Address the top hotspots. Implement **low- or medium-effort** fixes (Option A or B); no large refactors or unrelated files.
- **high**: Perform a comprehensive analysis. Address all significant hotspots that are actually backed by the profile data, and you may implement **medium- or high-effort** fixes (Option A, B, or C) where justified — but this is not license for open-ended refactors unrelated to the hotspots found.

For each application-code hotspot you decide to fix, briefly weigh three remediation tiers before choosing which one to implement in the patch:
- **Option A (low effort):** safe, localized tweaks — pre-allocating, avoiding redundant work, hoisting invariants out of loops.
- **Option B (medium effort):** algorithmic improvements or logic changes confined to the function/package.
- **Option C (high effort):** architectural changes or replacing a dependency.
Only implement the tier(s) permitted by the current reference level. If a higher-effort tier would fix the issue better but is out of scope for this reference level, mention it briefly in SUMMARY as a follow-up option rather than implementing it.

### SUMMARY

Structure this section as:

1. An "Executive Summary" markdown table, one row per hotspot you analyzed:

   | ID | File Path | Function | Self % (measured) | Max Theoretical Reduction* | Confidence | Priority (1-5) |
   |---|---|---|---|---|---|---|

   - `Self % (measured)`: the hotspot's self% (or cum%, if you're fixing the whole subtree beneath a call) exactly as reported in the analyzer result — a measured fact, not an estimate.
   - `Max Theoretical Reduction*`: an Amdahl's-law **upper bound**, equal to that same self%/cum% figure — the largest possible drop in total CPU time if this hotspot's cost were fully eliminated, assuming everything else unchanged. State which basis (self or cum) you used. Never present this as a predicted or guaranteed outcome, and never invent a number not directly derivable from the analyzer result.
   - `Confidence`: driven by the profile's total sample count (e.g. "Low (n=4)", "High (n=5000)") — low sample counts mean wide statistical uncertainty on the self%/cum% figures themselves, so say so here rather than in prose only.

## Using the `read_file` Tool

1. Use the `read_file` tool with a request like:
   - `read_file: main.go` — to read the entire file
   - `read_file: main.go:100-150` — to read lines 100-150 with surrounding context

2. The tool will return the file with line numbers. Use those line numbers when constructing your patch.
3. Keep using the tool until you have enough context to write an accurate patch.

Do NOT invent line numbers or file paths. Only write a patch for files you have actually read with `read_file`.
